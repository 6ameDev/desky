## 2. Key Design Decisions (best aspect per pillar)

### A. Inter-task comms: `SystemContext` + `EventBus` [from 02, with 01 loggability]

- `SystemState` struct (pitch, roll, distanceMM, `isPickedUp`, `cliffDetected`, `isDriving`, `RobotMode {MANUAL, AUTONOMOUS, LOW_POWER, EMERGENCY}`) protected by Mutex. Single source of truth.
- `SystemEvent { EventType, uint32_t payload, timestamp }` over FreeRTOS Queue. Types: `CLIFF_DETECTED, PICKED_UP, UDP_COMMAND, BATTERY_LOW, FACE_RECOGNIZED, USER_TOUCH`.
- **From 01:** log every Event with timestamp (`[00:12.420] CLIFF_DETECTED`) — primary debug tool.

```cpp
// Thread-Safe Global State Context [from 02]
struct SystemState {
  // Motion Data
  float pitch, roll;
  uint16_t distanceMM;

  // High-Level Flags
  bool isPickedUp;
  bool cliffDetected;
  bool isDriving;

  // Active Operating Mode
  enum RobotMode { MODE_MANUAL, MODE_AUTONOMOUS, MODE_LOW_POWER, MODE_EMERGENCY } mode;
};

// Asynchronous Event Notification System [from 02, + timestamp from 01 loggability]
enum EventType {
  EVENT_CLIFF_DETECTED,
  EVENT_PICKED_UP,
  EVENT_UDP_COMMAND_RECEIVED,
  EVENT_BATTERY_LOW,
  EVENT_USER_TOUCH,
  EVENT_FACE_RECOGNIZED
};

struct SystemEvent {
  EventType type;
  uint32_t payload;
  uint32_t timestampMs;
};
```

### B. HAL with `ISensor`/`IActuator` + Spec structs [from 03 — unanimous winner]

```cpp
// Abstract Sensor Interface [from 03]
class ISensor {
public:
    virtual bool init() = 0;
    virtual void update() = 0;
    virtual bool isEnabled() const = 0;
    virtual void setPowerState(bool enable) = 0;
    virtual uint32_t getTargetIntervalMs() const = 0; // Configured poll frequency
};

// Example Spec Encapsulation [from 03]
struct MPU6050Config {
    uint8_t i2cAddress = 0x68;
    float gyroBiasX = 0.0f;
    float accelThresholdG = 1.5f; // For pick-up detection
    uint32_t sampleRateHz = 50;   // 20ms polling interval
};
```

Why over `01/02` plain `drivers/*.cpp`: zero changes to fusion/behavior when swapping VL53L0X → VL53L1X / LiDAR. Only write a new driver class with updated specs (min/max range, timing budget).

### C. Sensor Fusion Engine [merge 01 semantics + 02 code rules]

Dedicated pure function `evaluateFusion(raw, state)`, no motor logic inside:

```cpp
void evaluateSensorFusion(const SensorReadings& raw, SystemState& state) {
  // Example Rule 1: Cliff Detection [from 02]
  // Validates distance + sudden acceleration drop to filter out false positives
  state.cliffDetected = (raw.tofDistanceMM > 150) && (raw.accelZ < 0.5f);

  // Example Rule 2: User Picked Up / Dynamic Interaction [from 02]
  state.isPickedUp = (abs(raw.pitch) > 45.0f || abs(raw.roll) > 45.0f) ||
                     (raw.accelMagnitude > 2.0f);
}
```

Additional rules [from 01]:

- `Status = f(ToF, MPU, IR)` — raw data is useless to behavior engine; it needs semantic signals.
- Single Sensor Signal: `ToF > 150mm` → `SIGNAL_CLIFF`
- Multi-Sensor Fusion Signal: `MPU acc > 1.8g` + `ToF > 150mm` → `SIGNAL_ROBOT_PICKED_UP_IN_AIR`
  - Note threshold divergence: 01 says 1.8g, 02/03 say 2.0g/1.5g — start at 1.8g, calibrate on hardware.
- Sensor + User Input: `User Joystick Forward` + `IR Front Obstacle` → `SIGNAL_DRIVE_OVERRIDE_BLOCKED`
- Future-proof: `Camera + Audio` → `FACE_RECOGNIZED` without touching fusion API.
- Other named signals [from 03]: `SIGNAL_CLIFF_HAZARD` (ToF ground drop + forward tilt), `SIGNAL_PICKED_UP`, `SIGNAL_OBSTACLE_AHEAD` (Front IR / ToF threshold).

These signals are published to the internal FreeRTOS Queue (Event Bus). Subscribed modules react immediately without polling hardware directly.

### D. Behavior: HFSM + Priority Arbitrator [01 state machine governed by 03 priorities]

To prevent conflicting commands (e.g. user pressing "Drive Forward" via UDP while a cliff is detected), use a **Priority Behavior Arbitrator** [from 03]:

1. **P1 Safety Override (Highest):** Emergency Stop, Cliff Fallback, Overcurrent Protection.
2. **P2 User Input:** Manual RC driving commands via UDP.
3. **P3 Autonomous Tasks:** Obstacle avoidance, line following, face tracking.
4. **P4 Idle/Ambient (Lowest):** OLED idle animations, power saving.

If a Priority 1 event occurs (`CLIFF_HAZARD`), it immediately preempts Priority 2 (User Input) and applies negative motor thrust regardless of app input.

States [from 01]: `STATE_IDLE`, `STATE_MANUAL_DRIVE`, `STATE_EMERGENCY_STOP`, extended with `AUTONOMOUS`, `SLEEP/LOW_POWER` per 02/03.

#### Behavior execution: intent fan-out (nobody centrally knows a behavior)

Multi-output behaviors (e.g. `HAPPY_WIGGLE` = wiggle motion + wiggle face
+ wiggle sound, all at once) are never orchestrated step-by-step — that
would serialize what must be parallel. Instead, execution decomposes along
the task boundaries from §F, so parallelism is structural:

1. **Coordinator decides WHAT, never HOW.** It sets
   `activeBehavior` in `SystemContext` and publishes one
   `EVENT_BEHAVIOR_STARTED{id, durationMs}`. It knows nothing about
   motors, OLED frames, or sound buffers.
2. **Each actuator subsystem owns a private behavior→primitive map.**
   `DRIVE_FORWARD` maps to forward-drive / neutral-face / silence;
   `HAPPY_WIGGLE` maps to wiggle trajectory / wiggle face animation /
   wiggle sound. Adding an output to a behavior touches exactly one map,
   never the coordinator.
3. **Conflicts resolve only where hardware is shared.** Drive-forward vs
   wiggle-motion both want the motors → the Priority Arbitrator above
   decides. Motors + display + sound want different hardware → no
   arbitration, they just run concurrently at their own task rates.
4. **Completion closes the loop for sequencing.** Actuators publish
   `EVENT_BEHAVIOR_DONE{id}` (duration expiry as fallback); the
   coordinator advances the HFSM. Sequencing exists behavior-to-behavior
   only — never output-to-output. Phase-tight sync (e.g. face winking on
   wiggle beats) is an explicit non-goal until observed missing.

### E. Power + I2C Manager [03 superset of 01/02 duty-cycling]

Rather than polling all sensors 100% of the time, components enter **Active**, **Standby**, or **Off** states based on current robot mode. Hardware drivers expose explicit `enable()` / `disable()` [from 02/03].

Per-state matrix [from 01]:

```plaintext
State: SLEEPING / IDLE
  ├── Camera: DISABLED (0% CPU)
  ├── ToF Sensor: SLEEP MODE (Polled 1Hz)
  ├── MPU6050: LOW-POWER ACCEL WAKE (Interrupt-only)
  └── Display: OFF or Dim Clock

State: ACTIVE_EXPLORING
  ├── Camera: ON (Feature Tracking @ 10 FPS)
  ├── ToF Sensor: CONTINUOUS HIGH-SPEED (20Hz)
  ├── MPU6050: FULL GYRO/ACCEL (50Hz)
  └── Display: Animated Face (25 FPS)
```

Refinements [from 03]:

- In "Manual Remote Driving" mode, ToF cliff sensor runs at low 10Hz safety check, microphone suspended.
- In "Idle/Docked" mode, motor drivers (`EEP` pin LOW) and ToF powered down completely, only MPU6050 awake at 5Hz for "shake-to-wake" tap event.

Manager behavior example [from 02]:

```cpp
void BehaviorCoordinatorTask(void* pvParameters) {
  SystemEvent event;

  while (1) {
    if (xQueueReceive(eventQueue, &event, portMAX_DELAY)) {
      switch (event.type) {

        case EVENT_UDP_COMMAND_RECEIVED:
          // User took manual control -> Pause high-overhead autonomous sensors
          sensorManager.setSensorEnabled(SENSOR_TOF, false);
          sensorManager.setSensorRate(SENSOR_MPU, RATE_50HZ);
          break;

        case EVENT_CLIFF_DETECTED:
          // Emergency Override: Instantly stop motors regardless of active mode
          motorDriver.emergencyStop();
          display.showWarning("CLIFF ALERT");
          break;
      }
    }
  }
}
```

Plus `I2CManager` time-sliced polling [from 03, missing in 01/02] to eliminate multi-device bus blocking and starvation.

### F. Dual-core task map [adopt 02/03, reject 01]

Reject `01`'s split (sensors Core 0 / vision Core 1). Adopt `02+03` isolation principle: **Core 0 = noisy comms, Core 1 = real-time control** to prevent WiFi/UDP jitter in motors and sensor dropouts.

| Core | Task | Rate / Prio | Source |
|------|------|-------------|--------|
| 0 | UDP Server + WiFi AP + Telemetry TX | High | 02 + 03 |
| 0 | Display / Audio (OLED/SPI, I2S mic/buzzer) | Med/Low | 02 (03 puts display on C1 — move to C0 if WiFi-stable, else C1 Task C @25FPS) |
| 1 | Motor / PWM + PID + e-stop | 100Hz Highest | 03 Task A |
| 1 | I2C Manager (I2C/SPI poll MPU/ToF/IR) + Fusion emit | 50/20Hz Med | 03 Task B + 01 Fusion Task |
| 1 | Behavior Coordinator (consume Event Queue, HFSM) | Med | 01 + 02 |
| 1 | Power Manager + Diagnostics | Low | 03 Task D |
| 1 (on-demand) | Vision (PSRAM frames, 10 FPS) | Low, only in EXPLORING | 01 Task 6 |

Detail [from 01]: Core 0 Real-Time Hardware & Perception vs Core 1 System State/Vision/Graphics was considered but rejected — heavy communication tasks must not share a core with motor PWM timing.

Detail [from 03]: Core 1 Task A (100Hz Motor), Task B (50Hz/20Hz I2C Manager), Task C (25 FPS OLED renderer), Task D (Power Manager & Diagnostics). Core 0: Async UDP, WiFi AP, heavy background compute.

### G. UDP Mobile Protocol [from 02 — only doc that specifies it]

To keep response times low, mobile app and robot exchange lightweight binary datagrams over UDP:

- **Control Packet (App → Robot @ 30–50 Hz):**
  `[Header: 0xAA][Mode: 1B][Throttle: 1B][Steering: 1B][ActionFlags: 1B][Checksum]`
- **Telemetry Packet (Robot → App @ 10–20 Hz):**
  `[Header: 0xBB][Pitch: 2B][Roll: 2B][Distance: 2B][StatusFlags: 1B][Checksum]`

## 4. Phased Build Plan

Merged non-breaking rollout from all three (stays functional throughout):

1. **Phase 1 — HAL + Foundation [03 Phase 1 + 01 Step 1 + 02 Phase 1]**
   - Create `ISensor`, `IActuator`, Component Spec structs.
   - Wrap existing DRV8833, VL53L0X, MPU6050 in HAL classes.
   - Move definitions to `config.h`, establish `SystemContext` with Mutex.
   - Draft base FreeRTOS Event Queue + simple 3-state engine (`IDLE`, `MANUAL_DRIVE`, `EMERGENCY_STOP`).

2. **Phase 2 — Async Scheduler + I2C Manager [03 Phase 2 + 02 Phase 2]**
   - Implement `I2CManager` time-sliced non-blocking poll for MPU6050 + VL53L0X in unified sensor task.
   - Set up Core 0 (UDP Comm) / Core 1 (Sensor/Motor loops) task layout per table above.
   - Wrap motor + I2C setup into separate FreeRTOS tasks.

3. **Phase 3 — Sensor Fusion + Power Profiles [01 Step 3 + 02 Phase 3 + 03 Phase 3]**
   - Build Pub/Sub Event Queue with timestamped logging.
   - Move cliff/tilt logic out of `loop()` into `SensorFusion`: combine IMU + ToF (+ IR) into `CLIFF`, `PICKED_UP`.
   - Implement fusion logic + dynamic polling rates / power matrix.

4. **Phase 4 — Arbitrator + UDP + UI [01 Step 4 + 02 Phase 4 + 03 Phase 4]**
   - Replace direct motor commands with Priority Arbitrator (P1 Safety > P2 User > P3 Auto > P4 Idle).
   - Add intent fan-out (§D): `BehaviorId` (`DRIVE_FORWARD`, `HAPPY_WIGGLE`, …), `activeBehavior` in `SystemContext`, `EVENT_BEHAVIOR_STARTED/DONE`, one behavior map per actuator subsystem.
   - Implement low-latency UDP binary packet protocol, tie packets to Behavior Coordinator.
   - Move OLED renderer to own task @ locked 25 FPS; add idle animations / warnings (`CLIFF ALERT`).

## 5. Open Questions (to address one by one)

1. **Target MCU:** ESP32 vs ESP32-S3 (PSRAM/camera needed for Vision task)?
2. **Display on Core 0 vs Core 1:** prefer Core 0 isolation, fallback to Core 1 @25FPS if WiFi starves it — OK?
3. **Camera/Audio now or stubbed?** Plan includes `ISensor` interfaces but Phase 1–4 can ship without them to keep bring-up fast.
